# _agents — wiki conventions

**Mode:** mixed
**Scope:** Reserved cross-cutting infrastructure for AI agents — profile pages, portable SKILL.md moves, per-agent memory syntheses, journals, and the global task queue.

## Tag vocabulary
- agent
- profile
- move
- pokemon
- skill

## Local conventions

This wiki holds four subfolders that are unique to the agent substrate:

- `profiles/` — one `profile-<pokemon>.md` per agent. Required fields: `pokemon_type`, `evolution_stage`, `moveset`.
- `moves/` — one **directory** per move (`moves/<move-id>/SKILL.md`). The SKILL.md format is the open standard shared by Claude Code, OpenClaw, Codex, Gemini CLI. Vault frontmatter is a superset; standard consumers ignore the extra fields.
- `synthesis/` — per-agent memory syntheses (`synthesis-<pokemon>-memory.md`), regenerated by `vault_refresh-profile-memory`.
- `trainers/` — one `trainer-<slug>.md` per entry in `~/.vault/stadium.toml` (only if you are using the Stadium training surface). See **Trainer pages** below.

Profile pages are exempted from the "id never changes" rule when undergoing evolution. The alias index at `_index/aliases.json` preserves historical references so reads through `vault_recall --by-agent` and `vault_channel-tail` still resolve aliased ids.

## Trainer pages

One file lives at `wikis/_agents/trainers/trainer-<slug>.md` for each `[trainer.<slug>]` block in `~/.vault/stadium.toml`. The file is the human-readable companion; the toml is canonical for routing.

**Frontmatter contract** (declared here; not promoted to the vault-wide canonical type list):

```yaml
---
id: trainer-<slug>
type: trainer            # wiki-local type for _agents/ only
title: "Trainer <slug>"
trainer_id: <26-char ULID>
trainer_slug: <slug>     # mirrors toml [trainer.<slug>]
wiki: _agents
status: active
created: YYYY-MM-DD
---
```

Required fields: `id`, `type`, `title`, `trainer_id` (26-char ULID), `trainer_slug`, `wiki`, `status`, `created`.

**`type: trainer` is wiki-local.** `vault_lint` outside `_agents/` will flag it as an unknown type — that is intentional. Do not add `trainer` to the canonical type list in the top-level `CLAUDE.md`.

Body is human-readable prose: accept policy, owned profiles list, last-match notes.

**Lint rules (`_agents/`-scoped, error severity):**

| Code | Triggered by |
|---|---|
| `TRAINER_FILE_MISSING` | toml `[trainer.<slug>]` exists, no matching `trainer-<slug>.md` |
| `TRAINER_TOML_MISSING` | `trainer-<slug>.md` exists, no matching toml `[trainer.<slug>]` block |
| `TRAINER_ID_MISMATCH` | `trainer_id` in toml != `trainer_id` in file frontmatter |

These rules only fire when linting `_agents/`. Other wikis are not inspected for trainer drift.

## Display configuration (optional)

Override default sprite color rendering and statusline type rendering for this vault. Both keys are optional; missing values fall back to defaults. Invalid YAML or out-of-range values are surfaced by `vault_lint` as `DISPLAY_CONFIG_BLOCK_INVALID` (severity: warning) and runtime falls back to defaults silently.

```yaml display_config
statusline:
  emoji_safe_mode: false      # default false; true -> text fallbacks ([psychic], [fire], etc.)
sprites:
  color_mode: truecolor       # default truecolor; one of: truecolor | ansi | none
```

- **`statusline.emoji_safe_mode`** — when true, `tools/start` writes `_index/statusline.json` with text fallbacks like `[psychic]` instead of emoji glyphs. Enable on terminals that render type emoji as tofu.
- **`sprites.color_mode`** — controls the colored half-block ASCII output of `core/sprites-runtime`. `truecolor` emits 24-bit RGB escapes; `ansi` falls back to the 16-color palette; `none` emits monochrome half-blocks (no escape codes).

## Source-type weights

Per-source-type weights applied by `vault_evolve-profile` when aggregating claim clusters by tag. Each claim's contribution to `cluster_weight` is multiplied by the weight for its `source_type` (`lived | curricular | retro`, default `lived`).

```yaml source_type_weights
lived: 1.0
curricular: 0.5
retro: 0.7
```

Defaults are baked in; the fence is optional. Any subset of the three keys overrides the default for that source type only — omitted keys keep their defaults. Invalid YAML or a non-numeric / negative value surfaces a runtime fallback to defaults; lint may report the malformed block separately in a future rule.

**Scope.** These weights affect specialty-cluster identification and the rationale rendered by `vault_evolve-profile` ONLY. They do NOT alter:

- The task-count eligibility gate (`tasks_completed >= N AND success_rate >= R` per `yaml evolution_thresholds`). Stage transitions still require lived task completions.
- `vault_agent-memory` ranking. Claims of all source types compete on full `effective_confidence`; the source_type tag in the rendered output is informational.
- `_index/claims.json` membership. The `by_source_type` bucket records each claim's type, unweighted.

The 1.0 / 0.5 / 0.7 default weights reflect: lived experience is the gold standard; curricular below half ensures a course-only profile cannot clear stage1 by curricular evidence alone; retro at 0.7 reflects real-but-not-fresh evidence.

## Courses (training material for fresh profiles)

A course is a `guide` page with a body convention that lists prerequisites, lessons, and the curricular claims an agent is expected to author on completion. No new note type; no course-running tool. The host LLM is the orchestrator.

**Naming.** Courses live at `wikis/<wiki>/guides/guide-course-<slug>.md`. The `guide-course-` filename prefix is the discoverability surface. Domain-specific courses live in the domain wiki (`wikis/<my-wiki>/guides/guide-course-<my-rules>.md`); cross-cutting agent-fundamentals courses live in `wikis/_agents/guides/`.

**Body format.** Five sections, in order:

1. **Overview** — why this course exists, who it is for, what it teaches (1-3 paragraphs).
2. **Prerequisites** — other courses to complete first (`[[guide-course-...]]` links), required real-work context, required readings.
3. **Lessons** — one `### Lesson N: <topic>` heading per lesson, each with three subsections: **Read** (linked pages/files/sources), **Do** (the exercise — usually "explore X and answer Y"), and **Claim to author on completion** (a fenced `vault_claim` invocation template the agent will run).
4. **Exit criteria** — N claims authored with this course as evidence; optional trainer promotion from `draft` to `active`; optional follow-on real-task completion.
5. **See also** — other courses, wiki-local moves the agent will invoke after this course, foundational concept/synthesis pages.

**Authoring claim invocations.** Each lesson's claim template uses `--source-type=curricular` and cites the course page as evidence:

```
vault_claim \
  --as=<agent-id> \
  --content="<lesson-derived assertion>" \
  --scope-wiki=<wiki> \
  --tags=<comma-separated tags> \
  --source-type=curricular \
  --evidence="[[guide-course-<slug>]]"
```

`source_type: curricular` is the substrate's signal that this evidence was taught, not lived. `vault_evolve-profile` applies the curricular weight (default 0.5) to these claims when computing specialty clusters; the task-count eligibility gate is unchanged (see Source-type weights above).

**Discovery.** `/recall course <topic>` does a substring match against page IDs and surfaces `guide-course-*` pages first. The operator or a dispatching trainer typically runs this to find an onboarding course for a fresh profile, then dispatches the profile to walk the lessons.

**Cold-start workflow.**

- Spawn a new profile; dispatch it to a relevant course via `/recall course <wiki>`.
- The profile reads the guide, walks each lesson, and authors curricular claims tagged with the course's `scope_wiki:` and `[[guide-course-<slug>]]` as evidence.
- After the course, dispatch the profile to a real task; `vault_agent-memory` returns its curricular claims at task-start, seeding cold-start context.
- Lived claims accumulate from real work; over time `evolve-profile`'s weighted cluster math qualifies the profile for stage1.

Lint does not check course-specific body shape — the convention is documentary. See the seed-bundled `guide-course-vault-mcp-onboarding.md` for a worked example, and stoa `docs/training-program.md` for the operator workflow.
